motor-led-mw

Motor control and LED middleware in C on Zephyr with TrustZone (TF-M), an Ethernet stack and PSA Crypto, plus an AI agent that writes the unit tests and runs them on the target, and (since v0.2.0) a battery management (BMS) module with SoC estimation validated on real cell data. All in QEMU (Arm MPS2 boards), no real hardware. Jump to: BMS module. Code: github.com/pavanyadava007/motor-led-mw

Node demo: speed over time

Signed UDP commands to the node in QEMU: +2000 rpm, rejected frames (replay, bad tag, wrong key, over limit), -1500 rpm, stop. Measured speed comes from the hall period, as the firmware sees it.

Mutation testing and the test agent

make mutants mutation-ref, make study report (results/mutants.json, results/ref_mutation.json, results/agent/*/summary.json, results/summary.md).

339 single-change mutants were generated from mlmw/src/*.c. 15 do not compile and 130 produce the same object code as the original (equivalent), so 194 mutants are used. They are split by a hash of their id into a TRAIN half (101), which the agent may see in mutant mode, and a HELD-OUT half (93), which only the scoring uses.

The hand-written reference suite (30 tests in tests/ref/) kills 149 of 194 (76.8 %), 72 of the 93 held-out mutants (77.4 %). Each suite runs on the emulated Cortex-M3 in about 0.5 s; a full mutation run takes under 3 minutes with 12 parallel QEMU workers.

What this shows:

• On its own the agent is weaker than a hand-written suite (best 49.5 % vs 77.4 %). No first-try file passed completely: the 30B model builds 92 % of its files first time but gets some expected values wrong when it works them out by hand from the header (LIN parity bits, CMAC frame layouts). Small tests matter: the cleanup removes a failing test, so one wrong number in a big test loses all its good checks.

• On-target feedback is the step that helps most: one shot to loop goes from 34.0 % to 46.2 % and the spread across seeds drops from 8.2 to 2.1 points. Mutant feedback adds a little more on average (49.5 %), with high variance.

• Added to the hand-written suite, the agent's tests catch 5 of the 21 held-out mutants the hand suite missed, in every seed (82.8 %). Three of them come up in all three seeds: an off-by-one in the LIN checksum loop that reads one byte past the buffer, a truncated reverse-commutation table, and an over-current debounce counter that is not reset. The other two differ by seed (a deleted clear-fault handler, a wrong sequence-number byte, a deleted LED calibration step, and others).

• The 7B model mostly fails to build (33 % of first-try files) and does not recover with feedback; at this size the agent loop does not pay off.

How the feedback works: the harness header tests/harness/include/mlmw_test.h gives EXPECT_EQ(actual, expected), which prints both values on failure. When a test fails on the current code, the agent sees the printed values and is asked to recompute the expectation from the spec. So the final suites are regression tests of the current behaviour: they protect what the code does now, and a spec bug that the agent accepts would need human review to catch. Each agent run (30B) takes about an hour, 51 model calls and 150k output tokens.

BMS module

Portable C99 battery management library for an N-series pack (default 12s of LG 18650HG2 cells, 10 ms cycle), written like flight-software prototypes are: no dynamic memory, no recursion, no OS or libc calls, every requirement traced to tests. What this shows:

• The EKF removes a 20 % initial SoC error that Coulomb counting keeps for the whole cycle: RMSE 0.57 to 0.86 % at 25 degC and 1.76 to 4.67 % at 0 degC, against about 20 % for Coulomb counting.

• At 0 degC the 1-RC model is the limit. The EKF error after 10 minutes reaches 6.62 % (HWFET), so requirement BMS-REQ-015 (5 % after 10 minutes at 25 and 0 degC) is not met at 0 degC; the traceability matrix shows it as failing. With a correct start and a 50 mA current-sensor offset, the EKF beats Coulomb counting on all 5 cycles at 25 degC but is worse on 5 of 6 cycles at 0 degC. A second RC pair, hysteresis and temperature-dependent parameters are the next steps.

• Target parity: the C code on the emulated Cortex-M4F (QEMU mps2-an386, FPU) produces bit-identical results to the x86-64 host on all 8,118,504 float32 outputs of these runs (-ffp-contract=off, no libm).

Limits

• No real hardware: the MCU is emulated (QEMU), there are no real cells in a pack, no AFE chip, no contactors, no CAN transceiver. Cell inputs in the unit tests are scripted; only the SoC study uses measured data, and that is one cylindrical cell from a lab tester, not an aircraft pack.

• Data: LG 18650HG2 from McMaster University (Kollmeyer et al.), CC BY 4.0. Two temperatures (25 and 0 degC), one parameter set per temperature (no interpolation between them). The reference SoC is itself Coulomb counting with the lab tester's 0.1 % current sensor. All drive cycles start from full charge at rest, which makes the EKF's start-up easy; a start from mid SoC under load is not covered by this data.

• The EKF does not model OCV hysteresis, a second RC pair, temperature inside a set, ageing or capacity fade, or cell-to-cell differences.

• Instruction counts are emulated, not cycles; timing on a real MCU (flash wait states, caches) will differ.

• Not certified. Not DO-178C compliant and not DO-254/ARP4754A work. It only borrows DO-178C-minded practices: written requirements, traceability to tests, structural checks (mutation testing), static analysis, deterministic numerics and reproducible results. The requirements are written for this demo, not taken from a real program.
